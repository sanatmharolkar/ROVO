Abstract

The communication link module of the Remote Driving Ontology (RDOnto) represents the connection between a remotely driven vehicle and the remote station as far as it matters for remote driving: end-to-end latency and its parts, latency limits per teleoperation setup, mode and speed, stability, connection loss, predictions, admissible speed and adaptations.

Introduction back to ToC

RDOnto, the Remote Driving Ontology, describes the context of remote driving (road vehicle teleoperation). It has three modules: the [operator awareness module](https://sanatmharolkar.github.io/RDOnto/docs/op/) (`RDOnto-op`), the [communication link module](https://sanatmharolkar.github.io/RDOnto/docs/link/) (`RDOnto-link`) and the [upper alignment module](https://sanatmharolkar.github.io/RDOnto/docs/core/) (`RDOnto-core`). SHACL shapes for incoming data and the Turtle files are in the [repository](https://github.com/sanatmharolkar/RDOnto). This module models the link only as far as it matters for remote driving. Network internals (cells, radio technologies, slices, QoS identifiers) are left out. Its main terms are: - **Session and streams.** A teleoperation session connects one station and one vehicle, with one operator, and carries that operator's engagements in sequence. Streams are named by their endpoints (vehicle to station, station to vehicle). - **End-to-end latency.** Latency is the sensor (glass-to-glass) latency plus the actuator latency, without the operator's reaction time. Each observation says which part it covers. - **Limits per setup.** The primary criterion is the distance the vehicle travels during the end-to-end latency, against a travel tolerance per teleoperation setup. Published millisecond budgets are reference budgets of the setup they come from. - **Connection loss and prediction.** Connection loss is silence on a continuously sent stream for longer than a timeout. Predictions of latency, data rate and connection loss have a source, a window and a confidence. - **Adaptations.** For each degradation the module states which adaptations address it, the conditions under which each is available, and a preference rank, so that queries can recommend one. The module imports the operator awareness module and reuses its terms (operator, vehicle, engagement, operation modes, configured limits, information channels). Design rules of the module: - **OWL 2 RL only.** Subclass, domain, range, subproperty and functional axioms, with disjointness and all-different axioms, so that the module can be used with forward-chaining rule engines. - **Times and durations are literals.** Times are `xsd:dateTime` and durations `xsd:dayTimeDuration` literals, so that a stream layer can compare them. - **Limits are configuration.** Every limit is an individual with a value in one fixed unit and a source. - **Current values are the latest observations.** How long an observation stays valid is decided by the stream layer; the ontology sets no maximum age. - **Interface terms.** Terms whose note starts with "Interface" belong to other modules (vehicle state, scene, teleoperation concepts and teleoperation ODD) and are declared here so that the module can be used without them.

connection timeoutc back to ToC or Class ToC

IRI: https://w3id.org/rdonto/link#ConnectionTimeout

Definition:

How long a stream with a given content may stay without data before the connection counts as lost. Value as qudt:numericValue with qudt:unit unit:MilliSEC.

Note:

LK-07. Connection loss is an absence of data, so it is a closed-world check against this timeout in the stream layer. Rule: only content that is sent continuously (isContinuous true) is tested and has a timeout. A stream is silent when the time since its lastReceivedAt, or since the session's prov:startedAtTime if it has never received data, exceeds the timeout for its content; a content without a timeout is never silent. The connection of a session counts as lost (RDOnto-link:ConnectionLost) when at least one stream is silent whose content the mode of the session's open engagement needs (neededInMode, for the mode or a broader mode); if the session has no open engagement but has carried one, when any of its streams is silent. A session that has not yet carried an engagement is not tested: before the first engagement a stream may be silent by design, e.g. no control commands are sent. It is lost since the earliest last data of those silent streams. The loss is detected later, when the timeout of the first of them runs out.

latency budgetc back to ToC or Class ToC

IRI: https://w3id.org/rdonto/link#LatencyBudget

Definition:

The largest acceptable value of a latency part in an operation mode, valid up to a vehicle speed. Value as qudt:numericValue with qudt:unit unit:MilliSEC.

Note:

LK-04 and LK-09. A reference budget: valid only for the setup it was measured or specified in (RDOnto-link:appliesToSetup), because published budgets are performance characteristics of particular setups [GA21b] and there is no standardization for ToD [SC22]. Which limits apply: take the limits of the session's setup for the mode of the open engagement, or failing that for its broader mode. Per latency part, the applicable budget is the one with the lowest upToSpeed at or above the current speed; a budget without upToSpeed covers every speed. (1) Each part with an applicable budget must be within it, and the sensor part within the setup's information age limit. (2) The budgets replace the travel tolerance only if they bound the end-to-end latency: an end-to-end budget, or an actuator budget together with an information age limit scoped to the setup. Otherwise the travel tolerance is checked as well. (3) If the setup has budgets of a part for the mode but the current speed is above every upToSpeed of them, the setup was not validated at that speed: the latency does not count as acceptable, and the admissible speed (LK-09) is at most the highest upToSpeed whose budget the latency meets. (4) A setup without any budget for the mode is judged by the travel tolerance alone. The vehicle-to-station part is RDOnto-op:InformationAgeLimit, scoped the same way, and is stated only in that form: a LatencyBudget covers the actuator latency or the end-to-end latency, never the sensor latency, so the check that a setup's limit is no looser than the mode's sees every vehicle-to-station budget.
