Abstract

The operator awareness module of the Remote Operation of Vehicles Ontology (R.O.V.O) represents a remote operator's awareness state of a remotely operated vehicle and its surroundings: what information is available to the operator, what the operator has perceived from it, how delayed and degraded it is, whether it is still valid, and whether it is sufficient for the situation awareness (SA) type of the operator's mode.

Introduction back to ToC

R.O.V.O, the Remote Operation of Vehicles Ontology, describes the context of remote driving (road vehicle teleoperation). It has three modules: the [operator awareness module](https://sanatmharolkar.github.io/ROVO/docs/op/) (`ROVO-op`), the [communication link module](https://sanatmharolkar.github.io/ROVO/docs/link/) (`ROVO-link`) and the [upper alignment module](https://sanatmharolkar.github.io/ROVO/docs/core/) (`ROVO-core`). SHACL shapes for incoming data and the Turtle files are in the [repository](https://github.com/sanatmharolkar/ROVO). This module represents the remote operator's awareness state, not the situation itself. Its main terms are: - **Operation modes and SA types.** An engagement is the period in which one operator is responsible for one vehicle in one mode: remote monitoring, remote assistance or remote driving. Each mode requires one SA type (supervisory, decision-support or operational). - **Two contexts of remote driving.** In event-based remote driving an event calls the operator in while something else drives the vehicle (its automated driving system or an on-board driver). In continuous remote driving the operator is the vehicle's driver for the whole trip. What starts the remote drive, not its duration, decides the context. - **Perception as an estimate.** What the operator has perceived is never asserted as fact: a perception assertion is an estimate about one situation element, backed by evidence such as eye fixations, probe answers or control inputs. - **Displayed scene and information age.** The scene shown to the operator is kept apart from the current scene at the vehicle. Information age and staleness follow from the capture, display and perception times. - **SA requirements and sufficiency.** Requirements per SA type state which types of element must be perceived and how recently, so that queries can judge whether the operator's SA is sufficient and which modes the operator can still perform. - **Operator state.** Workload, impairment, time on task and the fallback-ready state. The module uses PROV-O, SOSA and QUDT terms directly. Links to EDMC AUTO (SAE J3016) and A.U.T.O. are in the upper alignment module. The actuator latency that the module reads comes from the communication link module. Design rules of the module: - **OWL 2 RL only.** Subclass, domain, range, subproperty and functional axioms, with disjointness and all-different axioms, so that the module can be used with forward-chaining rule engines. - **Times and durations are literals.** Times are `xsd:dateTime` and durations `xsd:dayTimeDuration` literals, so that a stream layer can compare them. - **Limits are configuration.** Every limit is an individual with a value in one fixed unit and a source. - **Current values are the latest observations.** How long an observation stays valid is decided by the stream layer; the ontology sets no maximum age. - **Interface terms.** Terms whose note starts with "Interface" belong to other modules (vehicle state, scene, teleoperation concepts and teleoperation ODD) and are declared here so that the module can be used without them.
